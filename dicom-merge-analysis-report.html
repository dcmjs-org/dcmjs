Two parsers. One lazy core, one living shell.

A head-to-head audit of dicom-parser (the zero-copy, offset-based read core under Cornerstone's image loaders) and dcmjs (the full read/write, naturalize, SR/SEG manipulation library under OHIF) — what each does best, which should absorb the other, exactly which modules move, and what to optimize after the merge.

00 · Verdict

Merge dicom-parser into dcmjs — as its new layer-zero.

Recommended direction
Vendor dicom-parser's lazy offset tokenizer verbatim into the dcmjs repo as layer 0, exposed at a dependency-free dcmjs/parser subpath. Rebuild dcmjs's read path as a lazy materialization layer over it. Publish a final dicom-parser shim release that re-exports the subpath — no downstream consumer is ever forced to migrate.
The logic is asymmetric in both directions. dicom-parser's tokenizer is the only foundation from which the other library's behavior can be derived: given {tag, vr, dataOffset, length} you can lazily materialize dcmjs-style Values, but dcmjs's eager {vr, Value, _rawValue} model irreversibly discards offsets. Meanwhile dcmjs's assets — the write path, packed dictionary, charset handling, SR/SEG stack, and the only living CI/build/release infrastructure — are huge and non-portable, where the parser is ~160 KB of dependency-free ESM in 24 flat files whose 262 byte-level tests and fixture corpus travel with it. The code flows one way; the repo identity flows the other.
Lens · performance-first
dicom-parser → dcmjs

Parse speed depends on which code runs, not where it lives. Transplant the tokenizer verbatim, enforce non-regression with a CI benchmark gate against published dicom-parser 1.8.12. A fresh package invites "clean" rewrites of the hot loop — the single biggest perf risk.

Lens · ecosystem-first
dicom-parser → dcmjs

Both ecosystems pin by name. Hosting in dcmjs leaves OHIF untouched; image loaders are protected by a shim release of dicom-parser with identical API and UMD global. dcmjs's 0.x semver makes the core swap opt-in by default.

Lens · maintainability-first
new hybrid monorepo

Dissent: neither repo as base avoids inheriting structural debt; prefers a TypeScript-first layered monorepo with both names as shims. Its layered architecture is identical to the majority plan — adoptable incrementally inside dcmjs's existing pnpm workspace.

How to read the dissent. All three judges agree on the same end-state architecture (dicom-parser tokenizer at layer 0, lazy dcmjs data model above it, features as subpaths, adapters out). The disagreement is purely packaging. The pragmatic resolution: do the merge inside dcmjs (majority), but structure src/parser/ as a workspace package from day one so the hybrid end-state stays reachable without a second migration.
01 · Scorecard

Six dimensions, no ties.

Each dimension was analyzed by a dedicated agent reading both repos in full, with cited file:line evidence.

Parsing core architecture
dicom-parser

Offset-recording lazy tokenizer; allocation-free integer reads on a flat Uint8Array; single-pass sequence and fragment indexing; per-element warnings with partial-dataset recovery. dcmjs's eager model discards offsets and re-copies sequence items at every nesting level.

Performance & memory
dicom-parser

Wins header-only parse (~an order of magnitude less work and garbage per element), full parse with pixel data (seeks past pixels, zero-copy frame views vs per-frame ArrayBuffer copies), and memory (~1× file size vs ~2×+). dcmjs wins only bounded-memory streaming.

Data model & public API
dcmjs

Naturalized keyword datasets (dataset.PatientName) are what application developers want, with real engineering in round-trip fidelity (_rawValue write-back). dicom-parser's hex-tag accessors are clean and superbly typed but read-only and semantically bare.

Writing / serialization
dcmjs

A walkover: dicom-parser has zero write code. dcmjs ships a production-proven Part 10 writer — per-VR padding, encapsulation, lossless round-trip gate, large regression suite. Its flaws (copy-heavy buffers, re-fragmentation) are rework items, not disqualifiers.

Feature coverage
dcmjs

Dictionary, anonymizer, SR (TID300/1500), derivations (SEG/RTSS), charset decoding verified against the dclunie suite, streaming reader, adapters. Several would take person-years to recreate. dicom-parser's one superior slice: encapsulated pixel-data utilities.

Tooling, tests, ecosystem
dcmjs

Actively maintained (2026 commits vs dormant since 2023); pnpm 11 + rollup 4 + four GitHub Actions workflows + semantic-release with provenance, vs webpack 4 / karma / CircleCI Node 16. dicom-parser's portable wins: the testImages corpus, 262 byte-level tests, complete index.d.ts.

02 · Profile
dicom-parser ~24 src files · read-only · zero dependencies · powers @cornerstonejs/dicom-image-loader

The fast lazy core in an abandoned shell.

A single-pass tokenizer over one contiguous buffer that stores only {tag, vr, length, dataOffset} per element and decodes values on accessor calls. Its design is the performance ceiling of this merge; its packaging and upkeep are its floor.

Where it shines

  • Fully lazy materialization — elements are offset/length records (readDicomElementExplicit.js:34-50); values decode on access (dataSet.js:48-196). Parse cost and heap are independent of value sizes.
  • Zero-copy pixel data — encapsulated frames indexed as BOT + fragment offsets (findEndOfEncapsulatedPixelData.js:23-84); single-fragment frames return shared views, no copy (sharedCopy.js:15-22).
  • Offset fidelity — every element and sequence item records its byte range, including corrected lengths for undefined-length elements — the prerequisite for byte-exact passthrough rewriting.
  • Standards-correct edge handling — UN with undefined length parsed as implicit SQ per PS3.5 6.2.2 (readDicomElementExplicit.js:67-80); dictionary-free SQ peek heuristic; private implicit tags deliberately not recursed.
  • Malformed-file recovery — warnings array threaded through parsing; partial dataSet attached to thrown error (parseDicom.js:146-153); fragment lengths clamped to buffer end; missing DICM tolerated with explicit transfer syntax.
  • untilTag early exit at any nesting level — cheap header-only parses for viewers loading thousands of files.
  • Pluggable, dependency-free — deflate via injected inflater / node zlib / global pako; swappable big-endian parser; vrCallback dictionary hook.
  • Portable safety net — 262 byte-level unit tests, committed testImages corpus, complete hand-written index.d.ts.

Where it falls short

  • Read-only. No write or serialization path of any kind.
  • No character sets — strings decode byte-by-byte via String.fromCharCode (byteArrayParser.js:29-37); non-Latin SpecificCharacterSet is silently garbled.
  • No data dictionary — implicit-VR files yield vr: undefined unless the caller supplies a lookup; every consumer rebuilds value semantics.
  • Whole-buffer, sync only — no streaming, no async, deflate inflates the entire remainder eagerly on the main thread.
  • Latent crash bug — byteStream.warnings (an array) is invoked as a function on exactly the malformed files it should tolerate (findItemDelimitationItem.js:31, findAndSetUNElementLength.js:32).
  • Aged primitives — char-by-char string building, two typed-array allocations per float read, byte-by-byte multi-fragment frame assembly.
  • API footguns — string()'s element.Value escape hatch ignores the index argument (dataSet.js:180); out-of-range index throws TypeError; dead duplicated module still publicly exported.
  • Dead infrastructure — dormant since 2023; webpack 4 / karma / CircleCI Node 16; main and module both point at one minified UMD bundle; no exports map, no types field.
03 · Profile
dcmjs read + write + naturalize + SR/SEG/anonymize · powers OHIF & @cornerstonejs/adapters · active 2026

The feature stack and living infrastructure — on an eager core.

Everything layered above the tokenizer is here and battle-tested. The core itself eagerly materializes Value + _rawValue for every element, copies pixel frames, and discards file offsets — the exact properties the merge replaces.

Where it shines

  • Complete Part 10 writer — per-VR writeBytes with padding rules, implicit/explicit + both endians, encapsulated/fragmented pixel data with BOT, and a deliberate lossless mechanism: unchanged values written back from _rawValue (DicomMessage.js:244-267), gated by a 1400-line round-trip suite.
  • Naturalized data model — DicomMetaDictionary.naturalizeDataset gives keyword access, PN accessors, DICOM-JSON alignment; what OHIF and the adapters actually program against.
  • Packed dictionary system — base64-packed typed-array tables + binary search + lazy memoizing Proxy (dicom.packed.js, dicom.lookup.js, dictionary.fast.js): import cost measured 181 ms → 19 ms (9.5×). The best-engineered piece in either repo.
  • Streaming reader (new) — AsyncDicomReader + SplitDataView: chunked input, backpressure/drain, buffer freeing via consume(), Part10-without-preamble and raw LEI/LEE sniffing, untilTag, maxFragmentSize frame emission. Beta but well-tested (916 lines of async tests).
  • Charset correctness — TextDecoder-based SpecificCharacterSet handling verified against the dclunie test corpus.
  • Feature families with no dicom-parser equivalent — anonymizer, SR classes + TID300/TID1500 builders, derivations (Segmentation, ParametricMap, RTSS), normalizers, orientation/RLE/colors utilities, four viewer adapter families.
  • Living engineering system — pnpm 11 with supply-chain policies, rollup 4 ESM+UMD with exports map, four GitHub Actions workflows, semantic-release with npm provenance, dictionary generation pipeline with its own benchmark.

Where it falls short

  • Eager double materialization — every element stores both formatted Value and raw _rawValue (DicomMessage.js:110-111); offsets are discarded, pixel frames copied (ValueRepresentation.js:626-635), peak memory ~2×+ file size.
  • Hot-loop overhead everywhere — per-read findView linear scan + object allocation (SplitDataView.js:190-224); per-byte string building; per-element Tag objects and double toCleanString; scan-rewind-recopy sequence reader; noCopy option that still copies.
  • Round-trip footguns — private/unknown tags silently dropped on denaturalize (DicomMetaDictionary.js:294-304); scalar-vs-array instability from single-value collapse; magic _meta/_vrMap keys with inconsistent shape contracts.
  • Zero TypeScript — no types field, not a single .d.ts in the repo; downstream projects maintain their own partial typings.
  • Tree-shaking-proof monolith — namespace-object exports pull 4 adapter families, gl-matrix, ndarray, and ~370 KB of dictionary source into every bundle; private dictionary registered at import time.
  • Inconsistent error policy — silent fallbacks (unknown VR → OW, DS coerced to null), data-integrity violations logged below the default level, root-logger setLevel side effect at import.
  • API sprawl — deprecated shims warning since 0.24 still shipping at 0.49; legacy DICOMWEB class with a hardcoded third-party server; three coexisting data models, none documented in the README.
Already in motion. This dcmjs tree (current master) ships recent optimization work: the packed dictionary (PR #470, 9.5× faster load), AsyncDicomReader streaming, untilTag early-exit on read (PR #490), and deflate support in the async path. The merge plan below builds on that trajectory rather than fighting it — the remaining gap is precisely that the streaming reader still eagerly materializes every value, which dicom-parser's offset model solves.
04 · Target architecture

Four layers, one read path.

All three judges converged on this layering. Each layer is a real subpath export; lower layers never import upper ones; the dictionary is opt-in so the raw tier stays dependency-free and tree-shakable.

Layer 3
Adapters — out of core entirely

Cornerstone / Cornerstone3D / VTKjs / DICOMMicroscopyViewer adapters (gl-matrix, ndarray dependents) move to or stay in @cornerstonejs/adapters, repointed at the new layers. Upstream already extracted them for exactly this reason.

Features — separately importable subpaths

anonymizer · SR (src/sr + TID300/TID1500) · derivations (SEG, ParametricMap, RTSS) · normalizers · orientation · RLE/bitArray · colors · dicomJson. Characterization tests written before each port — derivations.test.js is currently empty. dicomweb.js is dropped (superseded by dicomweb-client).

from dcmjs
Layer 1
Data model — lazy materialization, write with passthrough, dictionary, streaming

Read: ValueRepresentation VR classes reworked to decode from {dataOffset, length} on demand, with cached decodes and TextDecoder charset handling wired into string accessors. Naturalize/denaturalize rebuilt over lazy elements with footguns fixed (no scalar collapse by default, private tags preserved). Write: dcmjs's per-VR writers on a single output stream with length backpatching, plus the new co-designed capability neither repo has: dirty-set tracking + byte-exact memcpy passthrough of untouched elements, SQ subtrees, and entire encapsulated pixel-data runs straight from the source buffer. Dictionary: the packed stack as an opt-in subpath, lazy-initialized, integer-keyed. Streaming: AsyncDicomReader's chunk/consume/listener model re-platformed onto the layer-0 tokenizer; SplitDataView confined here with a cached-chunk fast path.

06 · Migration roadmap

Twelve steps, safety net first.

Sequenced for minimum blast radius: every step before the core swap (step 8) is purely additive, and the swap itself ships behind dcmjs's 0.x semver so downstream opts in deliberately.

Vendor the raw tier, untouched by redesign

Copy dicom-parser's src/ into dcmjs src/parser/ as ESM. Only changes: fix the two warnings()-as-function crashes and the dataSet.string() index footguns; alias findAndSetUNElementLength for API compat. Behavior otherwise byte-identical.

Port the safety net before anything else

Commit the testImages corpus (~5.5 MB, offline-runnable), rewrite the 13 mocha/chai suites (~262 cases) as jest tests against src/parser/, bring index.d.ts in as the seed of a package types entry.

Stand up the non-regression gates CI

Benchmark gate parsing the committed corpus + a large multiframe: published dicom-parser@1.8.12 vs the vendored subpath — fail PRs on parse-time or peak-heap regression. Bundle-size assertion: importing dcmjs/parser pulls zero dictionary bytes.

Publish the subpath — purely additive release

Add "./parser" to the exports map as a side-effect-free, dictionary-free, pako-free entry; add a rollup UMD output emitting the dicomParser global. Ship as dcmjs 0.50.0; no existing consumer affected.

Convert dicom-parser to a shim

Replace its src with re-exports of dcmjs/parser matching the current export surface exactly (including deprecated names). Release 1.9.0, gated on integration smoke tests: the cornerstone image loaders parsing the full corpus and extracting encapsulated frames against the shim. Then move shim publishing into the dcmjs workspace and retire the old repo's pipelines.

Wire the dictionary as layer-0's optional vrCallback

Integer-tag-keyed lookups via the packed binary search; make _generateNameMap and private-dictionary registration lazy, off import time — so implicit-VR files get real VRs while the parser subpath stays dictionary-free.

Build the lazy bridge behind a flag

Rewire DicomMessage._read to consume tokenizer output and materialize Value/_rawValue lazily through the existing VR classes; route string decoding through the TextDecoder/SpecificCharacterSet path; cache decoded values on elements; adopt the numeric Tag internally.

Prove equivalence, then flip the default gate

Golden tests: old core vs new core (naturalized JSON + _rawValue) across both repos' corpora, the dclunie charset suite, malformed-file fixtures, and the 1400-line lossless-read-write suite. Then make the tokenizer-backed path the default (dcmjs 0.51.0), deleting the scan-rewind SQ reader and SplitDataView from the sync path.

Exploit offsets in the writer

Passthrough-rewrite mode: untouched elements memcpy'd from source byte ranges; VR writeBytes only for dirty elements; configurable fragmentSize with preserve-original-fragmentation/BOT default; deflate-on-write. Makes anonymize / tag-edit rewrites near-memcpy fast and byte-identical for untouched data — eliminating today's fidelity deltas by construction.

Re-platform streaming

Rebuild AsyncDicomReader on the shared tokenizer, keeping addBuffer/consume/listener semantics; fix the readUint16Array off-by-one and the noCopy copies; add the cached-chunk fast path to SplitDataView.

API hardening

Scalar-collapse and accessor Proxies opt-in; private tags preserved through naturalize/denaturalize; typed error hierarchy with strict/lenient modes and a machine-readable diagnostics array; extend .d.ts coverage across DicomDict/naturalized APIs; subpath exports with sideEffects: false.

Downstream coordination — optional, unforced

PRs to @cornerstonejs/dicom-image-loader offering a direct dcmjs/parser import; OHIF bump to the 0.51+ line; archive the dicom-parser repo. The shim remains published indefinitely; after two stable releases, remove the legacy eager-reader flag and dead code.

09 · Risks & CI gates

What can go wrong, and the gate that catches it.

Integration temptation

Rewiring the transplanted tokenizer onto dcmjs's BufferStream/SplitDataView would silently surrender the entire performance win. The contiguous-buffer sync path must keep dicom-parser's flat index arithmetic; SplitDataView is streaming-only.

CI benchmark vs published dicom-parser@1.8.12 on the committed corpus — parse time and peak heap fail the PR.
Lossless round-trip fidelity

The eager Value/_rawValue model is load-bearing for byte-faithful rewrites. Replacing it with lazy formatting risks subtle deltas (padding, DS "-0.000", dropPadByte semantics).

The existing 1400-line lossless-read-write suite must pass unmodified against the lazy layer before the old reader is removed.
Shim fidelity = the widest blast radius

Image loaders depend on exact semantics: the {exception, dataSet} throw shape, element field names, zero-copy frame views, the UMD global, even the bugs. Fixing the warnings() TypeError changes malformed-file behavior — ship it as a documented bugfix, not silently.

Integration smoke tests: both cornerstone image loaders parsing the full corpus against the shim before 1.9.0 publishes.
Semantic divergence between the two parsers

UN-as-implicit-SQ, fragment-to-frame mapping, charset normalization to ISO_IR 192, per-element warnings vs drop-the-rest recovery — swapping the core can change results for real malformed files.

Old-core vs new-core golden equivalence suite over both repos' fixture corpora, including the dclunie charset suite.
Default-path overhead eats the win

Import-time nameMap construction, private-dictionary registration, and per-element Proxies would make the merged high-level API slower than today's dicom-parser even with a fast layer 0.

Bundle-size CI assertion: importing dcmjs/parser pulls zero dictionary bytes; lazy-init enforced by the load benchmark.
Engines floor & environment split

dcmjs pins Node ≥ 22.13 and pnpm 11; image-loader consumers build on Node 18/20 LTS. The shim and parser subpath must not inherit the floor.

Shim package carries its own relaxed engines field and prebuilt UMD; verified in the publish workflow.
Known bugs riding along

dicom-parser: warnings()-as-function, string() index footguns, byte-by-byte fragment assembly. dcmjs: readUint16Array off-by-one (BufferStream.js:245-254), noCopy that copies, no deflate-on-write.

Each fix lands with its own regression test during the port — not after.
Two divergent read paths linger

The legacy eager reader behind a flag plus the new core means a long window of double maintenance, and the preliminary AsyncDicomReader adds a third path until re-platformed.

Hard flag-removal deadline (two releases) with the equivalence suite as the exit criterion.
One measured number to anchor expectations. The only benchmark that exists today is the dictionary load: 181 ms → 19 ms (9.5×), from dcmjs's own generate/bench-dictionary-load.mjs. Every other claim in this dossier is code-derived and code-verified, but unmeasured — which is why the roadmap puts the benchmark harness at step 3, before any hot-path code moves. Build the parse benchmarks first; let them arbitrate every optimization in section 07.
